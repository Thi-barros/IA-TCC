API de Detecção de Doenças Foliares em Alface

Serviço HTTP que expõe o classificador YOLO11-cls treinado neste trabalho. Recebe uma imagem de folha de alface (Lactuca sativa) e devolve a classe, a confiança e as três probabilidades — para que o back-end, o dashboard e o ESP32-CAM consumam a IA sem instalar PyTorch nem conhecer detalhes do modelo.

Escopo do serviço

Este serviço faz uma coisa: recebe uma imagem de folha e devolve a classificação. Tudo o mais é responsabilidade do back-end da aplicação, que consome esta API.

Faz

  • Classifica em saudavel / bacteriano / fungico
  • Devolve confiança e as três probabilidades
  • Indica se o alerta deve disparar
  • Gera mapa de calor Grad-CAM sob demanda

Não faz

  • Persiste na tabela deteccoes
  • Publica ou consome MQTT
  • Envia notificação push (RF07)
  • Autentica usuários

Início rápido

Suba o serviço e envie uma foto. O modelo é carregado uma única vez, na inicialização — a primeira requisição já responde quente.

1 · Subir o serviço

python -m uvicorn api.main:app --host 0.0.0.0 --port 8000

2 · Classificar uma imagem

curl -X POST -F "imagem=@folha.jpg" http://localhost:8000/analyze

As três classes

Os rótulos canônicos correspondem exatamente ao ENUM da coluna classe da tabela deteccoes: sem acentos, em minúsculas. Grave o valor de classe; use classe_exibicao na interface.

índice 2 saudavel Saudável sem patógeno Revocação medida: 0,9929
índice 0 bacteriano Bacteriano Xanthomonas campestris Revocação medida: 0,9717
índice 1 fungico Fúngico Bremia lactucae Revocação medida: 0,8462 — classe mais difícil

Não escreva esses rótulos à mão no front-end. Consulte GET /info, que devolve índice, rótulo canônico, rótulo de exibição e se há patógeno. Uma divergência de grafia grava dado inválido no ENUM do PostgreSQL sem gerar erro visível.

Endpoints

Quatro rotas no contrato: duas de operação e duas de inferência. Ambas as rotas de inferência aceitam ?heatmap=true e devolvem exatamente o mesmo corpo de resposta — mudam apenas no formato de envio.

GET /health Verificar disponibilidade do serviço ▶

Informa se o modelo está carregado e pronto para inferência. Adequado para health check de orquestradores e balanceadores. Não recebe parâmetros.

Responde 200 mesmo com o modelo fora. Uma falha de carregamento não derruba o serviço: ela é reportada aqui, em status: "erro" com a causa em detalhe. Verifique o campo, não só o código HTTP.

Resposta 200 · modelo carregado

{
  "status": "ok",
  "modelo_carregado": true,
  "modelo_versao": "yolo11n_cls_alface.pt",
  "dispositivo": "cpu",
  "detalhe": null
}

Resposta 200 · modelo indisponível

{
  "status": "erro",
  "modelo_carregado": false,
  "modelo_versao": null,
  "dispositivo": null,
  "detalhe": "Arquivo de pesos não encontrado: modelos/yolo11n_cls_alface.pt"
}

Devolve as classes reconhecidas e os parâmetros em vigor. Serve para o dashboard montar legendas e rótulos sem duplicar as definições de classe no front-end, e para descobrir em tempo de execução se o Grad-CAM está disponível e qual o limite de tamanho de imagem.

POST /analyze Classificar imagem enviada como formulário ▶

Classifica uma imagem enviada como multipart/form-data. Rota indicada para o dashboard web, para testes manuais e para clientes que já trabalham com formulários. Dispositivos embarcados devem preferir /analyze/raw.

Corpo da requisição · multipart/form-data

CampoTipoDescrição
imagem binary obrigatório Arquivo de imagem da folha (JPEG ou PNG). Máx. 10 MB por padrão.

Parâmetros de consulta

NomeTipoPadrãoDescrição
heatmap boolean false Inclui o mapa de calor Grad-CAM em heatmap_base64. Exige pesos .pt; com modelo .onnx a requisição responde 400. Consulte suporta_heatmap em /info antes de pedir.

Respostas

CódigoCorpoQuando
200RespostaDeteccaoClassificação concluída
400RespostaErroImagem inválida, corrompida ou vazia
413RespostaErroImagem acima do limite
422HTTPValidationErrorCampo imagem ausente
503RespostaErroModelo indisponível

Exemplo

curl -X POST -F "imagem=@folha.jpg" "http://localhost:8000/analyze?heatmap=true"
POST /analyze/raw Classificar imagem enviada como corpo bruto ▶

Classifica os bytes de imagem enviados diretamente no corpo, sem envelope multipart. Rota destinada ao ESP32-CAM: montar um multipart em microcontrolador consome memória e tempo, enquanto enviar o buffer JPEG cru é uma única chamada. A resposta é idêntica à de /analyze.

Corpo da requisição

image/png		 binary obrigatório Bytes da imagem, sem envelope multipart. Corpo vazio responde 400.

Parâmetros de consulta

NomeTipoPadrãoDescrição

O campo alerta

alerta é verdadeiro somente quando há patógeno e a confiança atinge o limiar — 0,85 por padrão, configurável. É o gatilho da notificação push do RF07.

Situaçãopatogeno_detectadoalerta
saudavel, confiança 0,99 false false
fungico, confiança 0,95 true true
fungico, confiança 0,60 true false

Use alerta para decidir o disparo da notificação; use patogeno_detectado para registrar a ocorrência no histórico, ainda que sem notificar.

Códigos de status

Todo erro devolve o mesmo corpo: um objeto com a chave detail.

CódigoSignificadoAção do cliente
200Classificação concluídaProcessar a resposta
400Imagem corrompida, truncada, vazia ou em formato não suportadoRecapturar a imagem
413Imagem acima do limite configuradoReduzir a resolução no ESP32
422Campo obrigatório ausenteCorrigir a requisição
500Falha inesperadaConsultar o log do serviço
503Modelo indisponívelVerificar /health; tentar novamente

O erro 400 é deliberado. Uma imagem ilegível nunca produz um resultado. Classificar silenciosamente um JPEG truncado como folha saudável suprimiria o alerta sem qualquer indicação de anomalia — a pior falha possível deste sistema. Trate o 400 como “recapturar”, jamais como “sem doença”.

Integração

Quatro consumidores previstos. O dashboard e o back-end usam /analyze; o ESP32-CAM usa /analyze/raw. 

# formulário
curl -X POST -F "imagem=@folha.jpg" http://localhost:8000/analyze

# corpo bruto, com mapa de calor
curl -X POST --data-binary "@folha.jpg" \
     -H "Content-Type: image/jpeg" \
     "http://localhost:8000/analyze/raw?heatmap=true"

# disponibilidade
curl http://localhost:8000/health
import requests

with open("folha.jpg", "rb") as arquivo:
    resposta = requests.post(
        "http://localhost:8000/analyze",
        files={"imagem": arquivo},
        timeout=10,
    )

resposta.raise_for_status()
deteccao = resposta.json()

if deteccao["alerta"]:
    # persistir em 'deteccoes' e acionar a notificação push (RF07)
    ...
const dados = new FormData();
dados.append("imagem", arquivo);

const resposta = await fetch("http://localhost:8000/analyze", {
  method: "POST",
  body: dados,
});

if (!resposta.ok) {
  const { detail } = await resposta.json();
  throw new Error(detail);
}

const deteccao = await resposta.json();

Para exibir o mapa de calor, use ?heatmap=true e monte a imagem assim:

<img src={`data:image/png;base64,${deteccao.heatmap_base64}`} />
#include <HTTPClient.h>
#include "esp_camera.h"

const char* SERVIDOR = "http://192.168.0.100:8000/analyze/raw";

void enviarImagem() {
  camera_fb_t* quadro = esp_camera_fb_get();
  if (!quadro) { Serial.println("Falha ao capturar"); return; }

  HTTPClient http;
  http.begin(SERVIDOR);
  http.addHeader("Content-Type", "image/jpeg");
  http.setTimeout(10000);

  int codigo = http.POST(quadro->buf, quadro->len);

  if (codigo == 200) {
    Serial.println(http.getString());   // JSON da deteccao
  } else {
    Serial.printf("Erro HTTP %d\n", codigo);
  }

  http.end();
  esp_camera_fb_return(quadro);
}

Substitua 192.168.0.100 pelo IP da máquina que executa o serviço. O servidor precisa ter sido iniciado com --host 0.0.0.0 para aceitar conexões externas.

Desempenho medido

Números medidos, não estimados. A inferência foi medida por 05_benchmark_latencia.py em 02/08/2026 — 100 imagens do split test, 10 inferências de aquecimento descartadas, AMD Ryzen (AMD64 Family 23 Model 24) em CPU, sem CUDA.

ConfiguraçãoMedianaMédiap95p99
PyTorch / CPU20,10 ms23,23 ms38,27 ms81,34 ms
ONNX / CPU12,73 ms16,15 ms32,69 ms78,98 ms

Medido pelo caminho HTTP completo, em 127.0.0.1 e com pesos .pt, a resposta ponta a ponta ficou em 53,3 ms — dos quais 40,6 ms de inferência e 12,7 ms de sobrecarga do HTTP. Ambos atendem ao RNF01 (< 100 ms). O número ponta a ponta é o mais representativo da experiência real do ESP32, ao qual se soma a latência da rede Wi-Fi local.

Duas decisões sustentam esse desempenho: o modelo é carregado uma única vez na inicialização, e a inferência roda em pool de threads, de modo que o laço de eventos permaneça livre para aceitar conexões e responder ao /health enquanto uma imagem é processada.

Estes números foram medidos no servidor de inferência, não em dispositivo embarcado. Na arquitetura proposta, o ESP32-CAM apenas captura e transmite a imagem; a inferência ocorre no servidor.
